cohort_retention.sql — CTE (drives the heatmap)not yet run
-- Core cohort retention query. For every signup cohort and every
-- months-since-signup offset actually observable by 2025-12-31,
-- what share of that cohort was an active Premium subscriber.
-- "Active" requires a convert event (trial drop-off shows up
-- immediately in month 0) and no cancel event before this offset.
-- Every row of this result is one cell of the heatmap above --
-- there is no separate hardcoded grid.
WITH subscriber_lifecycle AS (
  SELECT s.subscriber_id, s.cohort_month, s.signup_date,
    MIN(CASE WHEN e.event_type='convert' THEN e.event_date END) AS convert_date,
    MIN(CASE WHEN e.event_type='cancel' THEN e.event_date END) AS cancel_date
  FROM subscribers s LEFT JOIN subscription_events e ON e.subscriber_id=s.subscriber_id
  GROUP BY s.subscriber_id, s.cohort_month, s.signup_date
),
subscriber_offsets AS (
  SELECT subscriber_id, cohort_month,
    CASE WHEN convert_date IS NOT NULL THEN CAST((julianday(convert_date)-julianday(signup_date))/30.44 AS INTEGER) ELSE NULL END AS convert_offset,
    CASE WHEN cancel_date IS NOT NULL THEN CAST((julianday(cancel_date)-julianday(signup_date))/30.44 AS INTEGER) ELSE NULL END AS cancel_offset,
    -- how many months of history are actually observable for this cohort
    ((CAST(strftime('%Y','2025-12-31') AS INTEGER)-CAST(strftime('%Y',cohort_month||'-01') AS INTEGER))*12
      + (CAST(strftime('%m','2025-12-31') AS INTEGER)-CAST(strftime('%m',cohort_month||'-01') AS INTEGER))) AS max_observed_offset
  FROM subscriber_lifecycle
),
month_series AS (
  SELECT 0 AS m UNION SELECT 1 UNION SELECT 2 UNION SELECT 3 UNION SELECT 4
  UNION SELECT 5 UNION SELECT 6 UNION SELECT 7 UNION SELECT 8 UNION SELECT 9 UNION SELECT 10 UNION SELECT 11
)
SELECT so.cohort_month, ms.m AS months_since_signup, COUNT(*) AS cohort_size,
  SUM(CASE WHEN so.convert_offset IS NOT NULL AND so.convert_offset<=ms.m AND (so.cancel_offset IS NULL OR so.cancel_offset>ms.m) THEN 1 ELSE 0 END) AS active_count,
  ROUND(100.0*SUM(CASE WHEN so.convert_offset IS NOT NULL AND so.convert_offset<=ms.m AND (so.cancel_offset IS NULL OR so.cancel_offset>ms.m) THEN 1 ELSE 0 END)/COUNT(*),1) AS retention_pct
FROM subscriber_offsets so JOIN month_series ms ON ms.m <= so.max_observed_offset
GROUP BY so.cohort_month, ms.m ORDER BY so.cohort_month, ms.m;

churn_by_channel.sql — window functionsnot yet run
-- Cumulative churn by acquisition channel, month over month, plus
-- each month's worst-performing channel. Same SUM-OVER-running-frame
-- + RANK-OVER-partition pattern as the Aeroplan breakage query on
-- the Fintech side of this portfolio -- same shape of question
-- ("which segment loses value quietly"), different currency.
WITH churn_events AS (
  SELECT s.acquisition_channel,
    CAST((julianday(e.event_date)-julianday(s.signup_date))/30.44 AS INTEGER) AS churn_month_offset
  FROM subscription_events e JOIN subscribers s ON s.subscriber_id=e.subscriber_id
  WHERE e.event_type='cancel'
),
monthly_churn AS (
  SELECT acquisition_channel, churn_month_offset, COUNT(*) AS churned_count
  FROM churn_events WHERE churn_month_offset BETWEEN 0 AND 11
  GROUP BY acquisition_channel, churn_month_offset
)
SELECT acquisition_channel, churn_month_offset, churned_count,
  SUM(churned_count) OVER (
    PARTITION BY acquisition_channel ORDER BY churn_month_offset
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
  ) AS cumulative_churned,
  RANK() OVER (PARTITION BY churn_month_offset ORDER BY churned_count DESC) AS rank_in_month
FROM monthly_churn ORDER BY acquisition_channel, churn_month_offset;

Why this is the same analysis as the Lifecycle Churn System, just priced differently

A cohort retention heatmap and a live-service game's D1/D7/D30 retention curve are answering the identical question: of everyone who arrived in the same window, what fraction is still here N periods later? The gaming side of this portfolio's Lifecycle Churn System tracks that exact shape for Dead by Daylight — rage quits and loss streaks standing in for cancel events, D7/D30 standing in for months-since-signup. The mechanism underneath is a survival curve either way: steep early drop-off from the people who were never really committed, followed by a flattening tail of subscribers (or players) who've crossed whatever threshold makes them sticky.

The currencies just look different on the surface. A game studio prices retention in session frequency and eventual monetization; Spotify prices it directly in ARPU — €4.89/month per Premium subscriber, real and disclosed. But the query that produces both charts is structurally the same query: bucket by acquisition cohort, track survivorship over time, aggregate. The heatmap above and the churn dashboard on the gaming side could, with a few column renames, run on each other's schema.

The behavioural driver is the same too. Subscribers who survive their first renewal are dramatically less likely to churn later — RevenueCat's data shows renewal rates climbing from a 23–40% range at the first cycle to 56–70% by the third. That's the same "committed player" inflection the churn dashboard is built to detect: once someone crosses the early-risk window, the product has earned a different kind of trust, and the retention curve bends to prove it.

Industry benchmark, used to calibrate synthetic churn shape (RevenueCat State of Subscription Apps 2026)

Media & Entertainment trial-to-paid conversion spread: 11.5%–69.5% (wide variance category). Annual reactivation rate: ~5%, with monthly subscribers reactivating roughly 4× as fast. Renewal-rate progression across successive cycles: 23–40% median at the first annual renewal, rising to 44–64% at the second and 56–70% at the third. We use the shape of that progression — renewal risk falling the longer a subscriber survives — to build the monthly churn hazard curve in this dataset. We do not apply RevenueCat's annual-plan percentages directly as monthly numbers; Spotify Premium bills monthly, RevenueCat's cited figures are annual-plan-specific, and treating the two as equivalent would overstate the sourcing. The specific per-cohort retention percentages, subscriber population, plan-type mix, and acquisition-channel split are entirely synthetic, generated in-browser, and calibrated only to the general shape described above — not to any Spotify-specific number, because Spotify does not disclose cohort-level retention.

The database engine (SQLite via sql.js/WASM), the schema, and every query result on this page are real and re-executable — only the underlying subscriber population is synthetic.
